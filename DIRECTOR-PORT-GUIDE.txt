Encounter Director extraction and port guide
Current V18, reviewed 14 October 2026

The director is a standalone deterministic library. Copy dist/core as a unit.
It has no imports from the game, UI, display, browser storage or telemetry.
It accepts plain resolved content, opaque source IDs, tagged portal IDs, host
time and a spawn adapter. It emits data events and detached snapshots.

The implementation is JavaScript, not a drop-in C# or Unity component. The
algorithm and module boundaries can be retained during a C# translation.
No Last Epoch repository, Unity scene, actual asset loader, navigation system
or production spawn pipeline was modified or validated in this work.

Dependencies flow toward the director
------------------------------------
UI controller -> game host -> director core
UI controller -> display
UI renderers -> detached game/journal read models
Game host -> observational telemetry
Game and telemetry never import UI or display. Display never imports the game
or director. Core imports only other core modules. Tests enforce these edges.

Current baseline contract
-------------------------
The containing zone introduces its whole finite budget once. The ledger's
source metadata identifies that introduction; sources are opaque to the core.
Rooms have no owned fuel pool. First entry requests a portion from the zone's
remaining Potential into Available. The host property entryReleaseRequest is
a transfer instruction, not a room allocation. It is capped by remaining zone
Potential. Entry never tops up a shortfall simply because N+1 costs more.
The baseline requests 25 points in each chamber of a 100-point depth-1 zone.
Waiting in the first room can consume the entire zone's Potential through
passive flow. Later first entries can release zero. No reserve, replacement
wave, or implicit new fuel is created. Available residue is preserved.

Funding determines eligibility. A funded prepared group commits on the first
safe engine-ready update. Runtime recovery is uniformly one second in the toy;
it is not a personality parameter. Core warning default is 1.1s; the demo injects 6s.
An unfunded group forecasts affordability only if remaining introduced Potential
can cover its shortfall at the current effective flow rate. The selected door
blinks during that lead window. A bonus release that funds the group completes
any forecast without waiting for it. No fresh post-funding warning is required.

One prepared group persists through ordinary configuration changes. Resolved
members, actual prices and preferences are immutable. Menu changes affect
subsequent composition. A trigger is one pending intent, not a room or request
queue. Every successful spawn starts the technical recovery guard.

The host supplies portal IDs, tags and eligibility. The director ranks those
IDs using the prepared group's preferences and host safety checks. The host
creates exactly the designated units at the designated portal position.
The core receives neither room identity nor geometry or positions.

CURRENT BUDGET MODE
Construct with runtime:{budgetAwareComposition:true} for current design.
Default false is retained compatibility, not the current demo policy. New groups
fit Available+Potential. composition-budget.mjs folds a too-small terminal tail
into expandable groups; half the actual added cost transfers immediately.
Standalone membership stays fixed. Terminal ad hoc composition obeys hard limits.
budgetComplete records no further fundable group, with honest residue. New fuel
can resume it. It says nothing about living enemies. Boss go-time/stats live in
the game/ZoneHost and never enter this library or call beginFinalSpend.
The explicit beginFinalSpend API remains for compatibility tests/consumers only.

Host adapter and update sequence
--------------------------------
Construct EncounterManager({config, runtime}). Technical runtime options are
separate from encounter personality/content and immutable for that instance.
1. Apply host events once; update content and eligible portal descriptors.
2. Tick with an authoritative nonnegative simulation delta.
3. Supply assetsReady(group), canEnter(group, portalId) and
   commitSpawn(group, portalId) through the adapter.
4. Consume data events after the update. Expose staged actors only after
   spawn-committed; initiate asset preparation on group-prepared.
5. Notify actual defeats by their stable host actor IDs.
6. Render independent snapshots; UI clocks must not advance while paused.

assetsReady and canEnter are pure queries against the committed immutable group.
commitSpawn must create the complete group atomically, initially hidden and
noninteractive, or return failure and clean up all partial actors. Success must
return one unique nonempty string or safe integer actor ID per designated member,
with no collision against currently living IDs. IDs unique for the full activity
are recommended to prevent late death notifications from crediting reused IDs.
Malformed adapter output is a programming-contract error, not a recoverable
content choice. The director cannot undo arbitrary engine side effects.

A recoverable failure spends no fuel, preserves the prepared group and pending
intent, and does not reset recovery. A portal lost during a forecast cancels
presentation and permits safe re-selection without spending. An already-funded
group does not require a fresh warning when assets or a route become ready.
query snapshot.waitReason rather than parsing diagnostic English wait labels.
The UI never touches internal ledger, pending actor maps or living sets.

C# translation notes
--------------------
Use double for point amounts and simulation times when reproducing the current
JS reference, not Unity float. Preserve operation order and the 1e-7 affordability
tolerance; the conservation check uses 1e-5. If adopting fixed-point costs, make
that a deliberate separate change and rerun conformance tests.
Use HashSet<string> for tags/event IDs and Dictionary for resolved catalogs.
Use immutable/read-only DTOs for commitments and make explicit snapshot copies.
Map JS structuredClone/deepFreeze to DTO copying and readonly data ownership;
do not clone Unity objects or asset references into the library.
Use StringComparer.Ordinal for tie breaks. Preserve stable ordering between
successive preference-pruning passes. LINQ OrderBy is suitable; an unstable
List.Sort with unpreserved ties can choose different cores from the reference.
Translate nullable fundingEta and next/forecast states explicitly. -Infinity
last-spawn represents 'never spawned'; JSON encoding records it as null.
Bind a C# ISpawnAdapter equivalent around asset manifests, safe tagged portals
and the engine's atomic spawn transaction. Keep GameObjects, Transform,
MonoBehaviour, rendering, health, player pacing and rewards outside the core.
The event stream is synchronous; async engine work belongs behind readiness
queries. Apply events in a serialized authoritative update, not recursively
inside callbacks or concurrently with fuel commitment.

Known scope and remaining integration decisions
-----------------------------------------------
No C# port was compiled and no live Last Epoch integration was tested. Real asset
throughput, pooling, navigation, cancellation and transaction guarantees remain
for the engineering team to validate. This is not a technical stress laboratory.
The toy has one active zone and one effective passive rate. Concurrent-zone flow
policies require an explicit host policy rather than inferring them from this
Refuge route. Source-filtered releases are already supported by the ledger.
Scripted lieutenants, guardians and bosses are game-host actors outside Director
fuel. Journal results state this distinction so pressure and spending are not
mistaken for the same total. Ending early records remaining defenders without
granting defeats. Budget completion is not proof all enemies died.
Compatibility supports declared variant-ID pairs (including self-repeat bans).
The current illustrative catalogs declare no such pairs. More general engine
compatibility policies can be added as pure composer constraints with new tests.
Composition is deterministic; seeded card draws shape variety. Role mechanics
are abstract. Scripted bosses have separate host-only tuning; no combat stats or
player-power knowledge belongs in the Director. Current guides describe V17,
not the original DOCX. Historical snapshots remain evidence, not live contracts.
